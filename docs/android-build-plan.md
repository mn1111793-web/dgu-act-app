## Wrapper и повторяемость — будущие действия

1. В отдельном tooling-коммите этой feature-ветки изменить только AGP на 8.6.1 и добавить `.gitignore` для `.gradle/`, `**/build/`, `local.properties`, локальных SDK/ключей. Сейчас wrapper и эти правки НЕ созданы.
2. Получить официальный Gradle 8.7 bin; проверить SHA256 по [Gradle release checksums](https://gradle.org/release-checksums/). В пустом временном bootstrap-проекте проверенным Gradle создать wrapper командой `gradle wrapper --gradle-version 8.7 --distribution-type bin --gradle-distribution-sha256-sum <официальный_SHA256_8.7_bin>`. Заполнитель нужно заменить реальной сверенной суммой, не выполнять как есть. Не скачивать произвольный gradle-wrapper.jar из чужого проекта.
3. Перенести и проверить ровно четыре файла: `gradlew`, `gradlew.bat`, `gradle/wrapper/gradle-wrapper.jar`, `gradle/wrapper/gradle-wrapper.properties`. Проверить отдельный официальный SHA wrapper JAR; `distributionUrl` должен указывать на `https://services.gradle.org/distributions/gradle-8.7-bin.zip`, `distributionSha256Sum` — на соответствующую сумму bin ZIP. Проверить wrapper повторно после любого изменения. [Официальное руководство Wrapper](https://docs.gradle.org/current/userguide/gradle_wrapper.html) описывает механизм, его примеры новых версий не являются предложением обновить Gradle до них.
4. В локальном, исключённом из Git `local.properties` указать sdk.dir; JDK/SDK пути и credentials не коммитить. Зафиксировать отдельным отчётом ОС, JDK, SDK revisions, wrapper/distribution SHA, git SHA и чистоту дерева.
5. После разрешённого dependency resolution записать дерево зависимостей, включить и просмотреть checksum verification/lockfiles там, где поддерживается конфигурацией. Автоматически сгенерированные trusted checksums сначала сверять с происхождением артефактов; первая загрузка сама по себе не доказательство доверия. Не менять библиотеки на `+` или latest. [Android dependencies](https://developer.android.com/build/dependencies).

Повторяемая среда и зафиксированные зависимости не означают заранее побайтово идентичный APK: это нужно отдельно измерить двумя чистыми сборками. Ключи, timestamps и инструменты подписания также влияют на результат.

## Очередь команд после отдельного разрешения

Все команды ниже — **NOT RUN**, не инструкция выполнять их сейчас. Изолированная копия ветки; без подключённого рабочего планшета. В Windows использовать `gradlew.bat` вместо `./gradlew`.

```text
./gradlew --version
./gradlew :app:tasks --all
./gradlew :app:dependencies --configuration debugRuntimeClasspath
./gradlew :app:lintDebug :app:testDebugUnitTest --stacktrace
./gradlew :app:assembleDebug --stacktrace
```

До запуска проверить фактический граф задач (`--dry-run` после разрешения): даже задачи lint/test/configuration могут компилировать исходники и скачивать зависимости. В текущем этапе не выполнялась ни одна Gradle-команда. У `testDebugUnitTest` пока нет Gradle-набора `app/src/test`: успешная задача NO-SOURCE не заменяет 28 существующих host-групп и не означает Android regression PASS. При переносе тестов в Gradle не включать host shims в app/sourceSets. Существующие source-only runners требуют отдельно подготовленных инструментов, сами их не устанавливают.

После успешной debug-сборки: сохранить build log, exit codes, lint XML/HTML и перечень реально выполненных тестов; SHA256 APK; офлайн проверить package/version/targetSDK/manifest/signing certificate (`apkanalyzer`/`aapt`, `apksigner verify --verbose --print-certs`). Наличие APK не означает пригодности к установке. Если всё прошло, только после отдельного разрешения можно планировать `:app:assembleRelease` и закрытое подписание; без upload/release/магазина. `bundleRelease`, install/connected-тесты, очистка данных и произвольные clean/reset сейчас не нужны. Справочник задач: [Android command line build](https://developer.android.com/build/building-cmdline).

## Где тестировать и когда останавливаемся

Предпочтительно новый Android 13 emulator API 33 без реальных данных/аккаунтов либо отдельное тестовое устройство. Создание emulator и установка тестового APK — отдельное разрешение после build. Для проверки поведения target35 желательно затем дополнительное изолированное API35 окружение; минимальный API24 пока не объявлен проверенным. Фото, системный picker, клавиатура, ориентация, большой шрифт, SAF и печать проверяются вручную по [чеклисту](manual-acceptance.md). Эмулятор не подтверждает особенности камеры и файловой системы Ulefone.

Рабочие applicationId `com.example.dguactapp`, версии и signing сейчас не меняются. Debug APK подписывается debug key и не является совместимым обновлением установленного release. Для установки рядом на том же Android user нужен отдельный package, но debug applicationIdSuffix требует отдельного решения и сейчас не добавлен. Предпочтение — отдельный emulator/устройство, без риска для рабочего приложения. Нельзя обещать безопасную установку с тем же package на рабочий планшет.

Установленный user0 APK A (SHA256 `dfd8435ed2426f43f52695e0a0ce936e7b9771114c5e2067435de9778e6d06d1`, code1/name1.0) подтверждён владельцем. Его сертификат отличается от APK B; текущий исходный code2/name1.1 не доказывает совпадения с B либо установленной программой. Для возможного будущего обычного обновления нужны совместимые package/signing lineage, допустимый versionCode и совместимость данных/путей; проверка сертификата и версии не доказывает идентичность исходникам. Исходный ключ A должен оставаться у владельца в защищённом хранилище; **не присылать ключи и пароли в чат**. Без него обычное совместимое обновление не обещается. [Android app signing](https://developer.android.com/studio/publish/app-signing).

APK и исходники не содержат рабочую базу. PDF тоже не полный backup. Полное копирование/восстановление текущих private data не доказано; run-as был отклонён. Согласие не переносить старые данные не разрешает трогать существующую установку. Её сохраняем.

## Ограничения текущего локального этапа

- В модели сейчас запрещено повторное использование equipmentId между заявками. Поэтому требование «одна единица → несколько заявок при повторном ремонте» ещё не реализовано; две заявки с тем же serial и новыми equipmentId обходят это лишь дублированием, это не полноценная история оборудования. Нельзя объявлять полное ТЗ 1–19 готовым. Разрешить many requests для одной equipmentId и связанные проверки — отдельная адресная задача до приёмки такого сценария.
- Заказчик — текст внутри заявки, не общий справочник Customer. 1 заказчик/2 единицы/по3 акта проверены на host, экранный результат ещё нет.
- Сохранение синхронного JSON может замедляться с ростом истории. Orphan фото/PDF не удаляются автоматически; требуется оценка места и будущая безопасная уборка. Полный export/import базы отложен, share PDF его не заменяет.
- После неопределённого finishWrite нельзя показывать гарантированный rollback: перечитать состояние и сверить тот же ID. Host fault injection пройден, реальные firmware/ENOSPC/power-loss не проверены.
- Масштабный UI, новая БД, Google/ИНН/роли/SMS/каталоги остаются за пределами этапа.
